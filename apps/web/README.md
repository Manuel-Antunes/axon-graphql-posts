# `apps/web` — the test client

A Next.js (App Router) app that exists to **exercise the API**, not to be a product. Every page maps
to an architecture decision in `axonposts` and shows the result as it is — including when the result
is that something does not get through.

```bash
pnpm install                      # from the root: the app joins the pnpm workspace
pnpm --filter @axonposts/web dev  # http://localhost:3000
pnpm dev                          # from the root: brings up BOTH backends and this front end (nx run-many)
```

`.env.local` points at the `dev` stack on AWS. To run against the local backend, switch
`NEXT_PUBLIC_GRAPHQL_URL` to `http://localhost:8080/graphql`. **No CORS is needed**: the browser never
talks to the API — it talks to `/api/graphql`, this application's proxy (see below), and the one
crossing the boundary is the Next server.

The CORS that exists on the API Gateway (`infra/aws/support/http-api.ts`) stopped being necessary for
this client once the proxy landed. It stayed for anyone who wants to hit the API directly from a
browser.

## The rule that decides where everything lives

> **File organization is by FEATURE. Atomic design is by COMPOSITION.**

There is no `atoms/`, `molecules/` or `organisms/` folder. There is the route and what it needs:

```
src/app/
  _components/      what crosses features (post-card, post-list, tag-chip, site-header…)
  _providers/       SessionProvider + ApolloProvider
  actions/          "use server" — the ONLY door between this application and the identity provider
  feed/             page.tsx + _components/ + _hooks/
  posts/new/        page.tsx + _components/
  posts/[id]/       page.tsx + _components/ + _hooks/
  saga/  live/  me/  federation/  login/
src/components/ui/  the shadcn primitives (base-nova, on top of @base-ui/react)
src/lib/            what is not React: apollo/, auth/, env.ts
src/gql/            GENERATED by codegen. Do not edit, do not commit.
```

The leading `_` on a directory is how the App Router says "this is not a route". That is why
`_components` and `_hooks` can live inside `feed/` without creating `/feed/_components` as a URL.

The atomic scale still exists — it just is not a folder. `TagChip` is an atom, `AuthorByline` is a
molecule, `PostCard` is an organism, and the difference between them is **how much** each one asks of
the schema, not where the file sits.

## Fragment-based props: over-fetching as a compile error

The graphql-codegen `client-preset` generates *fragment masking*. In practice:

```tsx
export const TagChip_tag = graphql(`
    fragment TagChip_tag on Tag { id name }
`);

export function TagChip({ tag }: { tag: FragmentType<typeof TagChip_tag> }) {
    const { name } = getFragmentData(TagChip_tag, tag);   // only `id` and `name` exist here
    return <Badge>#{name}</Badge>;
}
```

`FragmentType<...>` is **opaque**. Even if the page's query brought back the whole post, TypeScript
refuses to let this component read any field outside its own fragment. And the page, on the other
side, enumerates no fields at all:

```graphql
query FeedPosts($first: Int!, $after: String) {
    posts(first: $first, after: $after) { ...PostList_connection }
}
```

The most direct demonstration of this is the `PostCard_post` / `PostArticle_post` pair: **the card
does not ask for `content`**. A feed of 20 posts that pulled each body would transfer the entire blog
to draw 20 titles. The one asking for `content` is the post page.

`unmaskFunctionName: "getFragmentData"` and not the default `useFragment`, because Apollo 4 has a
`useFragment` hook with a different meaning (reading a fragment from the cache). Two things with the
same name in an import would be permanent confusion — and this one is not a hook, it is a pure
function.

## `possibleTypes`: what the cache cannot deduce

`InMemoryCache` matches fragments **heuristically**. Reading `... on Author` off a cached object, it
has no way to know whether that object is an `Author` — the response only carries `__typename`, and
nothing says that `Author` implements `User`. Without help, it assumes a match.

In this schema that is not hypothetical: `me` returns the **interface** `User` (with `Author` and
`Reader`), and `_entities` returns the **union** `_Entity`. The map comes from the `fragment-matcher`
plugin:

```ts
// src/lib/apollo/cache.ts
import generatedIntrospection from "@/gql/possible-types";

new InMemoryCache({
    possibleTypes: generatedIntrospection.possibleTypes,
    typePolicies: { Query: { fields: { posts: relayStylePagination() } } },
});
```

Generated, and not hand-written, because a new type implementing `User` has to show up there without
anyone remembering.

## Page queries: `query.ts` + `PreloadQuery`

> **The query belongs to the PAGE, not to the hook.** It lives in a `query.ts` next to `page.tsx`, and
> both sides read it from the same place.

```tsx
// app/feed/page.tsx  (server component)
<PreloadQuery query={FeedPostsQuery} variables={{ first: FEED_PAGE_SIZE }} errorPolicy="all">
  <Suspense fallback={<FeedSkeleton />}>
    <FeedView />
  </Suspense>
</PreloadQuery>
```

```ts
// app/feed/_hooks/use-post-feed.ts  (client)
const { data, error, fetchMore } = useSuspenseQuery(FeedPostsQuery, {
  variables: { first: FEED_PAGE_SIZE },   // the SAME variables, or the cache will not match
  errorPolicy: "all",
});
```

The prefetch runs on the server with the client from `lib/apollo/rsc.ts`, which reads the ID token
from the `httpOnly` cookie and puts it in the header — so even an authenticated page (`/me`) renders
on the server without the token passing through JavaScript. The result comes across React's stream
(that is what `ApolloNextAppProvider` and the `InMemoryCache` from
`@apollo/client-integration-nextjs` are for), and `useSuspenseQuery` finds it in the cache instead of
asking again.

Three consequences worth knowing:

- **the variables are shared constants** (`FEED_PAGE_SIZE`, `LIVE_SNAPSHOT_SIZE`). If the server asks
  for 6 and the client for 10 there is no error — there is a second request, and only the network tab
  will tell;
- **`errorPolicy: "all"` on both sides.** With the default, an error becomes an exception in the RSC
  render and the whole route falls over. In this application the error is content: it shows up in
  place of the list, with the `code` the server translated;
- **`refetch` goes inside `startTransition`.** Without it, reloading a component that suspends
  unmounts the tree and the `fallback` comes back — the list flickers.

Not every page has a prefetch, and the exceptions say why: `/saga` measures a post that does not exist
yet when the page renders (prefetching a measurement would falsify it), and the `/live` subscriptions
never terminate, while `PreloadQuery` executes operations that do terminate.

## The proxy: `/api/graphql`

> **The browser knows only one address, and it belongs to the application itself.**

```
browser ──► /api/graphql ──► posts-api      (app/api/graphql/route.ts)
server  ────────────────► posts-api         (PreloadQuery, lib/apollo/rsc.ts)
```

Three things this solves, and none of them is "better organization":

1. **The ID token stops existing in the browser.** It is born in a server action, lives in an
   `httpOnly` cookie, and it is the *proxy* that puts it in the `Authorization` header. Before, it had
   to reach the page's memory for Apollo's `authLink` to assemble it; `lib/apollo/token.ts` and
   `links/auth-link.ts` disappeared because of this, and the `Session` type that goes down to the
   client no longer has the field.
2. **There is no CORS on the path.** Same origin: no preflight.
3. **There is ONE place where streaming can be solved** — the subject of the next section.

The **server** does not go through the proxy: making `PreloadQuery` open an HTTP connection to the
application itself would cost another Lambda invocation and latency, and there the cookie is already
at hand.

### Two rules that come from the topology, not from taste

This is an SSR *loopback*: the request already crossed this application's CloudFront before getting
here, and will cross it again on the way back. Both ends have limits.

- **Headers by ALLOW list, in both directions.** CloudFront stacks `cloudfront-viewer-*`,
  `x-amz-cf-*`, `x-amzn-tls-*`, `via`, `x-forwarded-*` on top of the browser's; forwarding everything
  blows the limit of the request it hands to the gateway, and the answer is a `403 "Bad request"` page
  — which reaches the client as an unexplained 403, with the user authenticated. On the way back,
  returning the gateway's infrastructure headers makes CloudFront reject the origin response with
  **502**.
- **The JSON path BUFFERS in both directions.** `new Response(upstream.body)` relays the `fetch`
  `ReadableStream` through Next's streaming function, and what comes out of there CloudFront rejects
  with 502. Reading the whole body produces a well-formed, fixed-size response. A GraphQL payload is
  small; the memory cost is nil. Whoever **needs** to stream — the subscription — builds its own
  stream instead of relaying the one from `fetch`.

## Subscriptions: they WORK, and what it took

The client sends `subscription onPostUpdated { … }` and receives the event. Against the stack on
Lambda. That took fixing **three** independent layers, and none of them was in the front end:

1. **the Quarkus handler does not stream.** `quarkus-amazon-lambda-http` is a
   `RequestHandler<APIGatewayV2HTTPEvent, APIGatewayV2HTTPResponse>` — the return type IS the whole
   response. The way out was not to fork it: it was to **not use it**. The `-Plambda-stream` profile
   packages the application as the HTTP server it is, and the **AWS Lambda Web Adapter** (an official
   layer) turns it into a function, with `AWS_LWA_INVOKE_MODE=response_stream`;
2. **the API Gateway does no response streaming in any mode.** Only a Function URL with
   `InvokeMode: RESPONSE_STREAM`. That is what `StreamingFunction` creates, and that is where
   `NEXT_PUBLIC_GRAPHQL_URL` points;
3. **the source was in-process.** `emitUpdate` reaches subscribers of its own container, and on Lambda
   the mutation necessarily lands in another one. Solved by **Axon configuration**, without touching
   the handlers: `PostCreatedEventHandler` and `PostUpdatedEventHandler` are still what they always
   were — an `emit` and nothing else — and their package (`application.post.event`) now runs in a
   *pooled streaming* processor, with an in-memory token store and an initial position at HEAD. Every
   container has its own cursor and reads the event store, which is the only place all of them see.

Measured in the browser, with the `/live` panel open and the mutations served by another container:

```
onPostCreated  00:10:31  live in the browser          v2 · saga closed
onPostUpdated  00:10:42  edited live in the browser   v3 · edited
```

### The proxy relays, and that is all

`/api/graphql` is a `fetch` and a `new Response(upstream.body)`. It does not interpret the protocol,
assembles no frames, and does not know what a subscription is — what reaches the browser are the bytes
`posts-api` wrote. The only thing it adds is the `Authorization`, read from the `httpOnly` cookie.

**There was an emulation here** — a polling loop reshaping the client's selection into a `post(id:)`
query — and it existed because the upstream was the API Gateway, which assembles the whole response in
memory. With the upstream on the Function URL with response streaming, the relay always works; an
alternative path that never executes is a path nobody fixes, so it went away.

**What holds this relay up is not in this file**: it is CloudFront's `OriginReadTimeout`, which a bare
`sst.aws.Nextjs` creates at 20 s and which a `posts-api` cold start (15–26 s, measured) blows through
with the proxy silent. The one that solves it is the `sst.aws.Router` in `infra/aws/edge/`: with the
site routed, SST mirrors the server's `timeout` onto the route's `readTimeout` — 60 s, CloudFront's
maximum.
<br>
The same router serves the subgraph at `/graphql`, and that is what will give both of them a domain
and a certificate the day there is one.

### Three numbers that were measured, not chosen

- **`axonposts.graphql.sse.keep-alive=2s`** in the `lambda` profile. `SseStream` writes the status on
  open, but Vert.x only sends the headers along with the first chunk of the body — which is the
  keep-alive. With the 15 s default, the proxy waited 15 seconds to discover something that was
  already ready;
- **a 360 s timeout** on the Next function, above `posts-api`'s 300 s. Whoever decides the end of the
  connection has to be the upstream: with a lower ceiling here, the one cutting it was AWS, and that
  reaches the browser as `Connection closed while having active streams`;
- **`retryAttempts: 5`** on the SSE client. The connection has an end — the upstream function has a
  timeout — and reconnecting is what turns an invocation ceiling into a seam nobody sees. (It was `0`
  while the upstream never opened the stream: there, each attempt cost the full deadline.)

## Authentication: server actions, and TWO providers behind one port

`src/app/actions/auth.ts` is the only door to the identity provider. The form posts to it, it signs
in with a password grant and stores **both tokens in `httpOnly` cookies**. The browser never sees the
refresh token, and the bearer only reaches the proxy — `/api/graphql` reads the cookie on the server.

**Which provider answers is decided by the environment, not by a build.** `lib/auth/provider.ts`
picks the OIDC one when `OIDC_ISSUER_URL` is set and Cognito otherwise; both implement
`PasswordIdentityProvider` from `lib/auth/identity.ts`. On AWS the variable is unset and nothing
about the deployment changed.

| | Cognito | OIDC (`OIDC_ISSUER_URL`) |
|---|---|---|
| where it is used | the deployed stage | dev against compose, and `apps/web-e2e` |
| endpoint | `InitiateAuth`, hard-coded | **discovered** at `/.well-known/openid-configuration` |
| the stored bearer | the **ID** token | the **ACCESS** token |
| where the roles are | `cognito:groups` | `realm_access.roles` |

**The two bearers are opposite, and both are forced by the issuer.** Cognito's access token carries no
`email`, which `UserProvisioning` needs, so that side stores the ID token. Keycloak puts
`realm_access.roles` only in the access token, and `posts-api` validates the access token, so a
session holding Keycloak's ID token would sign in and be refused on the first mutation.
`withTheAccessTokenAsBearer` in `lib/auth/oidc.ts` is where that side says so.

`lib/auth/claims.ts` reads the groups from `cognito:groups` and falls back to `realm_access.roles`,
which is what makes `isAuthor` — and therefore `/posts/new`, the `/saga` button and the header's
badge — work identically under both.

Three decisions of the Cognito path that cost an explanation:

- **`fetch`, not `@aws-sdk/client-cognito-identity-provider`.** The two operations used
  (`USER_PASSWORD_AUTH` and `REFRESH_TOKEN_AUTH`) are unauthenticated — they do not sign with SigV4.
  The SDK would drag ~2 MB into the function bundle to assemble a POST with two headers.
- **The password does not go through `/oauth2/token`.** Cognito's OAuth2 endpoint accepts
  `authorization_code`, `client_credentials` and `refresh_token`, but not `password`. It is the same
  path `infra/scripts/e2e.sh` uses.
- **The bearer is the ID token**, because Cognito's access token does not carry `email` and
  `UserProvisioning` requires one. What makes this safe is `quarkus.oidc.token.audience`, which checks
  `aud`. The Javadoc in `infra/aws/identity/index.ts` has the full decision.

The token is placed into `lib/apollo/token.ts` **during the provider's render**, not in a
`useEffect`: an effect runs after its children's effects, and it is a child that fires the first query
— the first request of every load would go out without `Authorization`.

## Build: Nx builds, OpenNext packages, SST publishes

```
nx run web:open-next-build
  └─ dependsOn: build      →  pnpm codegen && next build   (INFRA_PROVIDER=aws ⇒ output: standalone)
  └─ open-next build                                        (buildCommand: "exit 0" — does not rebuild)
```

`sst.aws.Nextjs` calls exactly that target (`buildCommand` in `infra/aws/web/index.ts`), which buys
Nx caching and a single definition of "how the site is built".

Two lines in `next.config.ts` exist because of this, and neither is tuning:

- **`outputFileTracingRoot: monorepoRoot`** — in a pnpm workspace, `node_modules` is a sea of symlinks
  to the root. Without pointing at it, Next picks a root heuristically and the bundle comes out
  missing packages; the symptom is `Cannot find module` at runtime, after a build that printed
  success;
- **`output: "standalone"` only with `INFRA_PROVIDER=aws`** — it is the format OpenNext packages, and
  there is no reason to pay for it on every local `next build`. The coupling with
  `buildCommand: "exit 0"` in `open-next.config.ts` is real and is declared in both files.

The `NEXT_PUBLIC_*` values are **inlined at build time**: switching environments is a rebuild, not a
restart. That is why the Nx `build` target declares those variables in `inputs` — without it the cache
would hand back a bundle pointing at the previous environment.

## Traps already paid for

- **DO NOT leave `next dev` running during a deploy.** The dev server rewrites `.next` continuously,
  and this project's `open-next.config.ts` has `buildCommand: "exit 0"` — it does not build, it
  PACKAGES whatever is in the directory. With dev up, what ships is a development build: the HTML
  starts referencing `/_next/static/chunks/main-app.js` (no hash, the name only dev uses), S3 answers
  `403`, the page does not hydrate, the form falls back to a native POST, and the server action dies
  with `TypeError: a[d] is not a function` in `webpack-runtime`. None of that points at the cause.

- **`@graphql-typed-document-node/core` has to be a DIRECT dependency.** The generated code imports
  it, and pnpm does not expose transitive dependencies. Without the line in `package.json`, every
  `graphql()` becomes `unknown` and the error shows up in the components, far from the cause.
- **The shadcn "base-nova" `Button` has no `asChild`.** The current style is built on
  `@base-ui/react`, and composing with another element is `render={<Link … />}` — `asChild` is Radix's
  API.
- **`useSearchParams` requires a Suspense boundary** so Next can pre-render the rest of the page.
  Applies to `/login` and `/saga`.
- **`secure: true` on the cookie kills local login.** Under `next dev` the origin is http, and the
  browser silently discards the cookie: the symptom is "the login does not stick". Hence
  `secure: process.env.NODE_ENV === "production"`. Careful: **if the shell exports
  `NODE_ENV=production`**, `next dev` breaks in two ways (PostCSS does not run and every page 500s,
  and the cookie goes out `secure`). Run it with `NODE_ENV=development pnpm exec next dev`.
- **Login: three things competed for the navigation, and only one could win.** `layout.tsx` reads the
  cookie, so the layout payload depends on it — and in production Next prefetches visible `<Link>`s,
  storing the ANONYMOUS layout while the user is still on the login screen. Any **soft** navigation to
  `/feed` reuses that payload: cookie written, server knowing who it is, and the header saying "Sign
  in". Under `next dev` (no prefetch) none of this shows up. The three sources of soft navigation,
  removed one at a time:
  1. `redirect()` inside the action itself;
  2. `revalidatePath("/", "layout")` in the action — it revalidates the CURRENT route, `/login`;
  3. and the one that survived the first two: **Next re-renders the current route after EVERY server
     action**, and `/login`'s `page.tsx` had `if (await readSession()) redirect("/feed")`. That
     redirect fired on its own, in the render that comes with the action's response, and unmounted the
     form before it could reload the page.

  The final design: the login page **does not redirect** (whoever already has a session sees a card
  saying so), and the form calls `signIn` **by hand** — not through `useActionState` — so that
  `window.location.assign` runs in the same *tick* as the response, with no intermediate render
  competing. A new session is a new document.
- **`Query.posts` is ASCENDING creation order.** `posts(first: 10)` are the ten OLDEST, and a post
  created now goes to the end of the list. The real-time panel was silent because of this: it was
  looking the other way. With no `last`/`before` in the schema, `/live` asks for the whole page (the
  ceiling is 100) and looks at the tail — with the limit declared in `app/live/query.ts`.
- **`relayStylePagination()` without `keyArgs` merges EVERY read of `posts`.** With the default
  (`keyArgs: false`), the `/live` read (`first: 100`) and the feed read (`first: 6`) become the same
  list in the cache, and the feed came back with a hundred cards. `keyArgs: ["first"]` separates the
  two without breaking "load more" (which only changes `after`).

## The pages, and what each one proves

| route | what it calls | what it proves |
|---|---|---|
| `/login` | the provider's password grant (server action) | the bearer the issuer requires; `aud` checked by the API |
| `/feed` | `posts(first:, after:)` | cursor connection + per-component fragments |
| `/posts/new` | `createPost` | born at **v1, with no tag** — the other service is what completes it |
| `/posts/[id]` | `post`, `updatePost`, `deletePost`, `restorePost` | partial update; **logical** deletion |
| `/saga` | `createPost` + probe | the v1 → v2 crossing, timed |
| `/live` | `onPostCreated`, `onPostUpdated`, `/live/stream` | what does not get through, and an SSE that does |
| `/me` | `me` | polymorphic interface + `possibleTypes` + account linking |
| `/federation` | `_entities(representations:)` | resolves by key, in batch, **without a token** |
